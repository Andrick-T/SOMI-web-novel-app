## Backend Foundation, API Contracts & Frontend Integration

You are working on the existing **SOMI** reading platform.

# 0. ABSOLUTE RULES

These rules have priority over everything else.

### DO NOT:

* Do not redesign the existing SOMI UI.
* Do not replace the current Reader UX.
* Do not reintroduce page-turn/page-flip functionality.
* Do not replace the current horizontal/continuous reading model.
* Do not rewrite the existing frontend architecture simply because you prefer another pattern.
* Do not delete working frontend features.
* Do not replace React/Vite/Tailwind unless absolutely required.
* Do not replace the existing routing system.
* Do not remove the repository/service/domain boundaries already established.
* Do not replace working mock repositories blindly.
* Do not connect UI components directly to database code.
* Do not put database queries inside React components.
* Do not create a giant `server.js` containing the entire backend.
* Do not hardcode production secrets.
* Do not silently change business rules.
* Do not invent API contracts that contradict the existing frontend domain models.
* Do not implement fake "production-ready" integrations using hardcoded success responses.

### DO:

* Inspect first.

* Test every layer.

# 12. ECONOMY API

This is a HIGH-RISK domain.

The server must be authoritative.

Never trust the client for:

* wallet balance
* coin balance
* chapter price
* entitlement ownership
* transaction status
* writer earnings

Implement:

GET `/api/v1/wallet`

GET `/api/v1/wallet/transactions`

GET `/api/v1/economy/packages`

POST `/api/v1/economy/purchases`

GET `/api/v1/economy/entitlements`

POST `/api/v1/chapters/:chapterId/unlock`

The unlock operation must be transactional:

1. Authenticate user.
2. Load chapter.
3. Determine authoritative price.
4. Check whether chapter is already free/unlocked.
5. Check wallet balance.
6. Deduct coins atomically.
7. Create transaction.
8. Create entitlement.
9. Commit transaction.
10. Return entitlement state.

If any step fails, rollback.

Prevent double spending and duplicate unlocks.

Use idempotency where appropriate.
